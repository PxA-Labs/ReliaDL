# ReliaDL Manifest Specification (v1.0)

> **Audience**: Systems Engineers, Security Auditors, Integration Developers
> **Status**: Specification Standard
> **Reading time**: ~15 minutes

---

## 1. Overview

The **ChunkGuard Manifest (`.cgmanifest`)** is a cryptographically signed, machine-readable catalog that defines the chunking topology, cryptographic hashes, and mirror locations for a downloadable artifact. 

While ChunkGuard can operate in *ad-hoc mode* (deriving chunk boundaries from HTTP `HEAD` metadata and trusting hashes on first download), the **Manifest Specification** provides:

1. **Pre-Authenticated Chunk Verification**: Every chunk's SHA-256 hash is known and cryptographically verified prior to downloading, eliminating "trust-on-first-download" risks.
2. **Merkle Tree Integrity**: Sub-chunk tree hashing enables immediate verification of partial streams before full chunk buffer completion.
3. **Multi-Source Failover & Mirroring**: Distributes chunk downloads across multiple CDN endpoints, cloud storage buckets, and peer mirrors.
4. **Supply-Chain Security & Provenance**: Cryptographic signatures (Ed25519 / RSA-PSS) guarantee the manifest was generated by an authorized publisher.
5. **Air-Gapped & Offline Verification**: Enables complete artifact verification in air-gapped environments without querying the origin server.

## 2. manifest File Format & Schema

### 2.1 File Encoding & Structure

* **File Extension**: `.cgmanifest` or `.cgmanifest.json`
* **Encoding**: UTF-8 without Byte Order Mark (BOM)
* **Format**: JSON (RFC 8259) or Canonical JSON (RFC 8785) when verifying signatures.

### 2.2 JSON Schema (Draft 2020-12)

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://chunkguard.org/schemas/v1/manifest.json",
  "title": "ChunkGuard Manifest",
  "type": "object",
  "required": [
    "manifest_version",
    "artifact_metadata",
    "chunking_topology",
    "chunks"
  ],
  "properties": {
    "manifest_version": {
      "type": "string",
      "const": "1.0.0",
      "description": "Semantic version of the manifest format"
    },
    "generator": {
      "type": "object",
      "properties": {
        "name": { "type": "string", "example": "ChunkGuard CLI" },
        "version": { "type": "string", "example": "1.0.0" },
        "timestamp": { "type": "string", "format": "date-time" }
      }
    },
    "artifact_metadata": {
      "type": "object",
      "required": ["filename", "file_size_bytes", "file_hash_sha256"],
      "properties": {
        "filename": { "type": "string", "example": "ubuntu-24.04-server.iso" },
        "file_size_bytes": { "type": "integer", "minimum": 0 },
        "file_hash_sha256": {
          "type": "string",
          "pattern": "^[a-f0-9]{64}$"
        },
        "file_hash_sha512": {
          "type": "string",
          "pattern": "^[a-f0-9]{128}$"
        },
        "content_type": { "type": "string", "example": "application/x-iso9660-image" },
        "custom_metadata": { "type": "object" }
      }
    },
    "mirrors": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["url", "priority"],
        "properties": {
          "url": { "type": "string", "format": "uri" },
          "region": { "type": "string", "example": "us-east-1" },
          "priority": { "type": "integer", "minimum": 1, "maximum": 100 },
          "headers": { "type": "object" }
        }
      }
    },
    "chunking_topology": {
      "type": "object",
      "required": ["default_chunk_size_bytes", "total_chunks", "hash_algorithm"],
      "properties": {
        "default_chunk_size_bytes": { "type": "integer", "minimum": 1048576 },
        "total_chunks": { "type": "integer", "minimum": 1 },
        "hash_algorithm": { "type": "string", "enum": ["sha256"] },
        "merkle_tree_root": {
          "type": "string",
          "pattern": "^[a-f0-9]{64}$",
          "description": "Root hash of binary Merkle Tree over chunk hashes"
        }
      }
    },
    "chunks": {
      "type": "array",
      "items": {
        "type": "object",
        "required": ["index", "start_byte", "end_byte", "size_bytes", "sha256"],
        "properties": {
          "index": { "type": "integer", "minimum": 0 },
          "start_byte": { "type": "integer", "minimum": 0 },
          "end_byte": { "type": "integer", "minimum": 0 },
          "size_bytes": { "type": "integer", "minimum": 1 },
          "sha256": { "type": "string", "pattern": "^[a-f0-9]{64}$" },
          "sub_blocks": {
            "type": "array",
            "description": "Optional 64KB sub-block hashes for granular streaming verification",
            "items": { "type": "string", "pattern": "^[a-f0-9]{64}$" }
          }
        }
      }
    },
    "signature": {
      "type": "object",
      "required": ["algorithm", "key_id", "signature_hex"],
      "properties": {
        "algorithm": { "type": "string", "enum": ["ed25519", "rsa-pss-sha256"] },
        "key_id": { "type": "string", "example": "key_release_2026_01" },
        "public_key": { "type": "string", "description": "Base64 or PEM encoded public key" },
        "signature_hex": { "type": "string" }
      }
    }
  }
}
```

## 3. Merkle Tree Root Hash Calculation

To enable single-root verification of entire chunk manifests, ChunkGuard calculates a binary Merkle Tree over all chunk SHA-256 hashes:

```
                      [ Root Hash (R) ]
                             │
              ┌──────────────┴──────────────┐
       [ Node H(0,1) ]               [ Node H(2,3) ]
              │                             │
        ┌─────┴─────┐                 ┌─────┴─────┐
    [ Leaf 0 ]  [ Leaf 1 ]        [ Leaf 2 ]  [ Leaf 3 ]
    (Chunk 0)   (Chunk 1)         (Chunk 2)   (Chunk 3)
```

### Algorithm

1. **Leaf Nodes**: For each chunk $i \in [0, N-1]$:
   $$\text{Leaf}_i = \text{SHA-256}(0x00 \mathbin{\Vert} \text{chunk\_sha256}_i)$$
   *(Note: The `0x00` prefix prevents second-preimage attacks between internal nodes and leaves).*

2. **Internal Nodes**: For adjacent node pairs $(L, R)$:
   $$\text{Parent} = \text{SHA-256}(0x01 \mathbin{\Vert} L \mathbin{\Vert} R)$$

3. **Odd Number of Nodes**: If a level has an odd count, the solitary right-most node is duplicated or promoted up one level:
   $$\text{Parent} = \text{SHA-256}(0x01 \mathbin{\Vert} L \mathbin{\Vert} L)$$

4. **Root Hash**: The single top-level node hash becomes `merkle_tree_root`.

## 4. Digital Signature & Provenance

### 4.1 Canonical Signing Procedure

To sign a manifest:
1. Strip the `"signature"` block if present.
2. Canonicalize the remaining JSON document per [RFC 8785 (JSON Canonicalization Scheme - JCS)](https://datatracker.ietf.org/doc/html/rfc8785).
3. Compute the cryptographic signature over the canonical UTF-8 bytes:
   * **Ed25519**: `Ed25519Sign(private_key, canonical_bytes)`
   * **RSA-PSS**: `RSAPSSSign(private_key, SHA-256(canonical_bytes))`
4. Append the `"signature"` block containing `algorithm`, `key_id`, and `signature_hex`.

### 4.2 Verification Flow

```
[ Load .cgmanifest ] ──▶ [ Extract signature & public key ]
                                    │
                                    ▼
                      [ Strip signature block ]
                                    │
                                    ▼
                      [ JCS Canonicalize JSON ]
                                    │
                                    ▼
                      [ Verify Ed25519 / RSA-PSS ]
                         ├── [FAIL] Invalid ──▶ Raise ManifestSignatureMismatchError
                         └── [PASS] Valid   ──▶ Proceed with Verified Chunk Download
```

## 5. Multi-Source Mirror Resolution

When a manifest specifies multiple `mirrors`, ChunkGuard distributes chunk downloads across mirrors using priority and health weights:

```python
def select_mirror_for_chunk(chunk_index: int, mirrors: list[MirrorSpec]) -> str:
    """
    Selects optimal mirror based on priority ranking, worker load,
    and historical failure rates.
    """
    healthy_mirrors = [m for m in mirrors if m.is_healthy]
    # Sort by priority (1 = highest)
    sorted_mirrors = sorted(healthy_mirrors, key=lambda m: m.priority)
    return sorted_mirrors[chunk_index % len(sorted_mirrors)].url
```

If an HTTP 5xx or timeout occurs on mirror A for chunk $k$, the retry handler automatically switches to mirror B for the subsequent retry attempt.

## 6. CLI Operations for manifests

### 6.1 Generate a manifest

```bash
# Describe a local artifact with 16 MB chunks and 64 KB sub-blocks
reliadl manifest generate \
  --file "./dist/ubuntu-24.04-server.iso" \
  --chunk-size 16MB \
  --output "./dist/ubuntu-24.04-server.iso.cgmanifest" \
  --mirror "https://cdn1.example.com/ubuntu-24.04-server.iso" \
  --mirror "https://cdn2.example.com/ubuntu-24.04-server.iso"
```

Sub-block digests are included by default and are what make localized repair
possible; `--no-sub-blocks` omits them, after which a corrupt chunk costs a full
re-fetch. `--sub-block-size` overrides the 64 KB default.

### 6.2 Create a signing key

```bash
reliadl manifest keygen --output "~/.reliadl/release_ed25519.pem"
# writes release_ed25519.pem and release_ed25519.pem.pub
```

### 6.3 Sign a manifest

```bash
reliadl manifest sign \
  --manifest "./dist/ubuntu-24.04-server.iso.cgmanifest" \
  --key "~/.reliadl/release_ed25519.pem" \
  --key-id "release-2026-q3"
```

The manifest is signed in place. `--algorithm` accepts `ed25519` (default) or
`rsa-pss`.

### 6.4 Download using a manifest

```bash
reliadl download \
  --url "https://cdn1.example.com/ubuntu-24.04-server.iso" \
  --output "/downloads/ubuntu-24.04-server.iso" \
  --manifest "./dist/ubuntu-24.04-server.iso.cgmanifest"
```

The manifest supplies the chunk partition, so the engine adopts those boundaries
and `--adaptive-chunks` has no effect — the digests are computed over these
specific ranges. With sub-block digests present, a corrupt chunk is abandoned at
the first bad 64 KB block and only the remainder is re-requested.

### 6.5 Verify a manifest and a local file

```bash
reliadl manifest verify \
  --manifest "./dist/ubuntu-24.04-server.iso.cgmanifest" \
  --file "/downloads/ubuntu-24.04-server.iso" \
  --public-key "~/.reliadl/release_ed25519.pem.pub"
```

Three independent checks are reported separately: the Merkle root against the
chunk list, the signature against the canonicalized document, and (with
`--file`) the artifact's own SHA-256. Exit status is non-zero if any fails.
Omitting `--public-key` still checks the signature, but against the key the
manifest carries — which proves integrity, not provenance, and is labelled as
such in the output.

## 7. Python SDK Integration

```python
from chunkguard.manifest import manifestManager, Chunkmanifest

# Load and verify manifest
manager = manifestManager(trusted_public_keys_dir="./keys")
manifest: Chunkmanifest = manager.load_and_verify("ubuntu.iso.cgmanifest")

print(f"Artifact: {manifest.artifact_metadata.filename}")
print(f"Total Chunks: {manifest.chunking_topology.total_chunks}")
print(f"Merkle Root: {manifest.chunking_topology.merkle_tree_root}")
print(f"Signature Validated: {manifest.is_signature_valid}")
```
