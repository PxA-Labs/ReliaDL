    ReliaDL: Algorithms and Their Provenance¶

    This document describes the algorithms actually implemented in reliadl/, states which are prior art and which are our own composition, and records the evidence behind every tuned constant.

    Nothing here is claimed as a research contribution unless it is marked as one, and no claim appears without either a citation to prior work or a reproducible measurement in this repository.

    Status legend¶

    Status Meaning
    Wired Called on the live download path in reliadl/download_engine.py
    Library Implemented and unit-tested, but not yet reachable from a download
    Planned Not implemented. Listed only so its absence is unambiguous

    1. BL-DCS: Bandwidth-Loss Closed-Loop Dynamic Chunk Sizing¶

    Status: Library — reliadl/algorithms/adaptive_chunker.py

    Provenance: standard square-root cost tradeoff. Our contribution is the per-segment loss rescaling, not the formula.

    Problem¶

    A chunk size that is too small pays per-request overhead on every range GET. A chunk size that is too large wastes more bytes when a chunk must be re-fetched. The optimum depends on the path, which changes during a transfer.

    Formulation¶

    Minimizing the per-byte cost of a transfer over chunk size S:

    J(S) = tau_overhead * mu / S  +  p_seg * S / MSS

    where tau_overhead is per-request overhead (s), mu is throughput (B/s), p_seg is the per-segment drop probability and MSS the maximum segment size. Setting dJ/dS = 0 gives the familiar square-root form. The controller adds a bandwidth-delay term so a fast, clean path is not throttled by request overhead:

    S* = clamp( gamma * sqrt( tau_overhead * mu_k * MSS / (8 * p_k + eps) )
            + lambda * mu_k * tau_k,
            S_min, S_max )

    The MSS factor inside the radical is what makes the radicand a byte-squared quantity, so the root yields bytes rather than the unit-dependent sqrt(bytes) of the bare form. The result is quantized to a power of two for allocator and page alignment.

    This is the classic square-root tradeoff between a fixed per-batch cost and a cost linear in batch size — the same first-order argument that produces the economic order quantity. We do not claim the form as novel.

    What is ours¶

    The metrics collector observes failures per chunk, while the loss model is expressed per segment; at an 8 MB chunk the two differ by roughly four orders of magnitude. Closing that loop with the transfer size that produced the observation,

    p_seg = 1 - (1 - p_chunk) ** (MSS / S_observed)

    converts a measured chunk failure ratio into the per-segment rate the radical expects (adaptive_chunker.py:267-272). Without it the controller is dimensionally incoherent in practice even though the formula looks right on paper.

    The concurrency constraint¶

    The cost model above describes a single sequential stream. Nothing in it mentions parallelism, and that omission dominates in practice.

    Aggregate throughput for a parallel downloader is roughly (chunks in flight) x (per-connection rate). A chunk large enough that fewer than W of them remain leaves some of the W workers with nothing to do, and the parallelism lost costs far more than the per-request overhead saved. The unconstrained controller walks straight into this: on a clean path it sees no loss, grows the chunk towards its 64 MB ceiling, and starves the pool.

    Measured, 64 MB file, 4 workers, median of 5 seeds. The two arms were interleaved within one process so that drift in machine load fell on both equally:

    Scenario Floor off Floor on
    clean 28.8 MB/s 52.1 MB/s +81%
    heterogeneous 28.7 MB/s 53.9 MB/s +88%
    failover 3.6 MB/s 8.9 MB/s +146%
    lossy 43.9 MB/s 46.1 MB/s +5%

    Unconstrained, the controller was around 45% slower than a fixed 4 MB chunk size, and on failover a single 32 MB chunk landing on the degraded mirror stalls everything queued behind it.

    The fix caps the issued chunk at remaining_bytes / workers, so at least W chunks always remain:

    S = min( S_BLDCS, max(S_min, remaining / W) )

    The cap only ever shrinks a chunk, so the loss-driven lower bound the controller computes is untouched; this constrains the solution without replacing the model. Implemented in reliadl/scheduling.py::_apply_concurrency_floor, with DynamicChunkPlanner.rewind_to returning the bytes a shrunk chunk gave up so the partition stays contiguous.

    This is the one genuinely new piece of modelling in the project. The square-root tradeoff is textbook; stating that it is wrong for a parallel downloader unless constrained by the worker count, and showing the size of the error, is not something the chunk-sizing literature appears to cover.

    It should be read for exactly what it is, though. The floor repairs a large regression; it does not make adaptive sizing a win. Against a fixed 4 MB chunk the constrained controller reaches parity on a clean path, is better on failover, and is modestly worse on lossy and heterogeneous -- 4 MB simply happens to suit this workload. The controller would have to earn its place on paths where a good fixed size is not known ahead of time, and a single file size with a single worker count cannot demonstrate that. See EVALUATION.md.

    Open issues — do not cite this controller until these are resolved¶

    • DEFAULT_GAMMA = 1.0 and DEFAULT_LAMBDA = 1.0 (:48, :51) are the only free parameters of the formula and both are unjustified placeholders. Neither has been swept or fitted.
    • The factor 8.0 in the denominator at :302 does not appear in the derivation above and is unexplained; it may be a bits/bytes slip. It must be derived or removed.
    • DEFAULT_OVERHEAD_SECONDS = 0.025 (:54) is described as "nominal" and has no measured source.

    There is no convergence proof and no optimality bound for this controller. It is a closed-form static optimum recomputed per decision epoch from a smoothed state estimate, not an online learning algorithm with a regret guarantee.

    2. EXP3.S Mirror Routing¶

    Status: Library — reliadl/algorithms/mirror_bandit.py

    Provenance: EXP3 and EXP3.S are Auer, Cesa-Bianchi, Freund and Schapire (2002). The implementation and the decay measurement are ours; the algorithm is not.

    Why an adversarial bandit¶

    When a file is available from several CDN edges or replicas, an edge's throughput depends on other tenants' load, routing changes and cache state — none of which are stationary, and none observable. Only the reward of the mirror actually used is observed; the counterfactual throughput of the others is unknowable. That makes this a bandit problem, and it motivates an algorithm that assumes nothing about the reward distribution: no independence, no stationarity.

    The algorithm¶

    p_{m,t}   = (1 - eta) * w_{m,t} / sum_j w_{j,t}  +  eta / M
r_hat     = r / p_{m,t}
w_{m,t+1} = w_{m,t} * exp(eta * r_hat / M)

    The uniform eta/M floor keeps every mirror under occasional test and bounds every selection probability away from zero, which is what makes the importance-weighted estimate r/p finite. Dividing by the selection probability is what keeps the estimate unbiased.

    Weights are held as logarithms and rescaled so the largest is exactly 1. This is a requirement, not a refinement: the per-round exponent is bounded by 1, but it accumulates, so a weight can grow like e^T over T rounds, and a long download makes tens of thousands of range requests. Rescaling leaves the selection distribution untouched, since it depends only on weight ratios.

    Tracking a moving target¶

    Classic EXP3 has vanishing regret against the best fixed arm, which is the wrong target here: over a long transfer the best mirror changes. The EXP3.S decay mixes each weight back toward the mean every round,

    w_m <- (1 - alpha) * w_m + (alpha / M) * sum_j w_j

    capping how much evidence any arm can hoard. With alpha = 0 the behaviour is exactly classic EXP3.

    Measured evidence for the decay default¶

    Regret against the best mirror in hindsight; three mirrors, eta = 0.1, averaged over 24 seeded trials of 5000 rounds, under a stationary schedule, an abrupt mid-transfer failover, and a gradual drift. The reward stream is seeded independently of the router's own sampler — sharing a seed makes the two draw identical values in lockstep and couples each reward to the arm that draw selected, which quietly favours whichever mirror sits first in the cumulative distribution.

    decay     stationary   switching   drifting   worst
0                217        1709        771    1709
0.0002           246         378        222     378
0.0005           279         390        235     390
0.001            333         426        256     426
0.002            420         494        311     494
0.004            578         633        397     633

    Classic EXP3 wins the stationary column and is unusable everywhere else. Any small positive decay cuts worst-case regret by more than four times, for about a tenth more regret in the stationary case. The optimum sat at alpha = 0.0002, which is 1/T for the 5000-round horizon measured — the EXP3.S guidance alpha ~ 1/T — and this was confirmed at T = 1000, 2000, 10000. decay_for_horizon applies that relationship.

    A reduced version (12 trials) runs in CI: tests/unit/test_mirror_bandit.py:577-674 asserts sublinear regret and that tracking beats classic EXP3. The exact table above is not yet reproducible from a committed script; that is tracked as benchmark work.

    DEFAULT_EXPLORATION_RATE = 0.1 is hardcoded and has not been tuned.

    3. Straggler Detection and Range Bisection¶

    Status: Library — reliadl/algorithms/work_stealer.py

    A chunk is a straggler when its projected time-to-completion, TTC = remaining / throughput, exceeds a multiple of the minimum TTC across active transfers. The baseline deliberately excludes idle workers, which would otherwise drag the reference down and mark healthy transfers as stragglers. A detected straggler's outstanding range is split at the midpoint of its unfetched remainder, not of the original range, so already-received bytes are not re-requested.

    reliadl/algorithms/task_deque.py implements a Chase-Lev-shaped work-stealing deque. Its docstring states plainly that it is lock-based, not the lock-free original (Chase and Lev, SPAA 2005); it approximates the interface, not the memory-ordering guarantees.

    4. Merkle Tree Integrity, Signed Manifests, and Sub-Block Localization¶

    Status: Wired (localization and manifest verification) — reliadl/manifest.py, reliadl/download_engine.py

    Tree construction¶

    A binary Merkle tree over chunk hashes with domain separation — SHA-256(0x00 || leaf) and SHA-256(0x01 || left || right). Inclusion proofs (get_proof, verify_inclusion) compare roots in constant time. Manifests are canonicalized per RFC 8785 and signed with Ed25519.

    The published root additionally commits to the leaf count:

    root = SHA-256(0x02 || uint64_be(leaf_count) || tree_root)

    This closes a real second-preimage weakness. Odd nodes are paired with themselves, so [a, b, c] and [a, b, c, c] built identical internal nodes and therefore the same root — and the manifest signs that root. The collision was verified to exist before the fix and to be closed after it (tests/unit/test_merkle.py::test_second_preimage_duplicated_tail_rejected). Binding the count was chosen over the Certificate Transparency promotion rule because it leaves the tree shape, and therefore every existing audit path, intact.

    Sub-block localization¶

    When a manifest supplies per-sub-block digests (default 64 KB), the engine streams each chunk through SubBlockStreamValidator. Each sub-block is checked as it completes, so a corrupt chunk is abandoned at the first bad block rather than after the whole range has arrived, and the verified prefix is kept. The retry re-requests only from the bad sub-block onward.

    Measured. A single flipped byte in sub-block 40 of a 64-sub-block, 4 MB chunk:

    Verification Bytes re-fetched
    Whole-chunk SHA-256 only 4096 KB
    Sub-block localization 1536 KB

    Pinned by tests/unit/test_integrity_localization.py.

    The bound, stated honestly¶

    The saving depends on where the corruption falls, because the retry resumes from the bad sub-block rather than re-fetching only that block. Bytes re-fetched are chunk_size - k * sub_block_size for a corruption in sub-block k, so:

    • corruption in the last sub-block: saves nearly the whole chunk;
    • corruption in sub-block 0: saves nothing — the same cost as no localization (test_corruption_in_the_first_sub_block_saves_nothing);
    • uniformly distributed corruption: saves about half the chunk on average.

    This is well short of the 1 - s/B (99.95%) figure an earlier revision of the documentation claimed, and the gap is structural, not an implementation detail.

    The open question this raises. Reaching a position-independent cost of one sub-block per corruption requires not aborting: verify the whole chunk, collect every bad sub-block, then re-fetch exactly those ranges. That trades the bandwidth saved by aborting early against a smaller retry, and it also slows detection of a mirror that is corrupting data, since the stream runs to completion before the verdict. Which side wins depends on corruption rate, chunk size and sub-block size, and it is not obvious a priori. That tradeoff is unmeasured here and is the most interesting thing in this area.

    Remaining gaps¶

    • Localization needs a manifest; without one the engine can verify only the whole file at the end, and a corrupt byte is attributable to no chunk.
    • get_proof / verify_inclusion still have no production call site. The engine checks sub-block digests directly rather than via inclusion proofs, which is sufficient because the manifest is signed as a whole.

    5. Supporting Mechanisms¶

    Mechanism Module Provenance
    EWMA RTT / throughput estimation, sliding failure window algorithms/metrics_collector.py Smoothing and variance ordering follow RFC 6298
    Token bucket rate limiting rate_limiter.py Standard. Tokens derive from elapsed time on consultation, so there is no timer to drift or cancel
    Three-state circuit breaker with capped exponential backoff algorithms/mirror_bandit.py Standard pattern
    SOCKS5 and HTTP CONNECT tunneling adapters/proxy_adapter.py RFC 1928, RFC 1929
    Streaming SHA-256/384/512, constant-time compare hash_verifier.py FIPS 180-4; hmac.compare_digest
    Exponential backoff with jitter download_engine.py:643-652 Standard

    6. Not Implemented¶

    Earlier revisions of this document described five "novel contributions" that were not present in the source. They are listed here so their absence is unambiguous, together with the prior art each would have to be built on and cited against.

    Described previously Reality Prior art it would rest on
    AdaChunk via Lyapunov drift-plus-penalty, with an O(1/V)–O(V) theorem Not implemented. BLDCSController is explicitly stateless (adaptive_chunker.py:147-150); drift-plus-penalty requires a virtual queue carried across slots Neely (2010)
    LtHash homomorphic aggregation, O(1) whole-file verification Not implemented. Whole-file verification is an O(N) disk re-read (hash_verifier.py:179-186) Bellare and Micciancio (1997); Lewi et al. (2019)
    Predictive parity injection under a Gilbert-Elliott channel Not implemented. No FEC of any kind exists Gilbert (1960); Elliott (1963)
    Whittle index restless-bandit scheduling, with an indexability theorem Not implemented. The router is EXP3.S, a different algorithm class — no subsidy, no indexability argument Whittle (1988); Weber and Weiss (1990)
    Sub-chunk Merkle localization Now implemented (section 4), though the saving is position-dependent, not the 99.95% originally claimed Merkle (1987)
