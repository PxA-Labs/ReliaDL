    1. ReliaDL Data Flow and System Architecture¶

    This document specifies the data flow, state transitions, and architectural interactions within the ReliaDL download system (formerly ChunkGuard).

    2. End-to-End Sequence Architecture¶

    The components involved, with their current integration status (see ALGORITHMS.md for provenance and open issues):

    • Transfer engine (wired): parallel HTTP range GETs with resume, per-chunk SHA-256 verification and atomic state checkpointing.
    • BL-DCS chunk sizing (library only): closed-loop chunk size from measured bandwidth, RTT and loss.
    • EXP3.S mirror routing (library only): adversarial-bandit selection among replicas, with a circuit breaker and health monitor.
    • Straggler detection and range bisection (library only): splits the unfetched remainder of a lagging chunk.
    • Merkle tree over chunk hashes (manifest and CLI audit only): inclusion proofs in Ed25519-signed manifests.

    No forward error correction, homomorphic hashing, or restless-bandit scheduling is implemented. Earlier revisions of this document claimed all three.

    sequenceDiagram
    participant User
    participant DL as Download Engine
    participant SM as State Manager
    participant W as Worker Pool
    participant HV as Hash Verifier
    participant FW as Sparse Writer

    User->>DL: download(URL, output, expected_hash?)
    DL->>DL: HEAD / probe: size, Accept-Ranges, ETag
    DL->>SM: load or create resume state
    SM-->>DL: completed chunk set
    DL->>DL: plan_chunks(file_size, chunk_size_bytes)
    loop for each pending chunk, bounded by max_parallel_workers
        DL->>W: range GET [start, end]
        W->>FW: pwrite(offset, bytes) as the stream arrives
        W->>HV: incremental SHA-256 over 64 KB buffer
        alt digest matches
            HV-->>DL: chunk verified
            DL->>SM: checkpoint chunk complete
        else digest mismatch or transport error
            HV-->>DL: verification failed
            DL->>DL: discard whole chunk, retry with backoff + jitter
        end
    end
    opt expected whole-file hash supplied
        DL->>HV: re-read assembled file, O(N)
        HV-->>User: verification result
    end

    3. State Machine Formalisms¶

    3.1 Download State Machine¶

    stateDiagram-v2
    [*] --> INITIALIZED
    INITIALIZED --> PLANNING : probe size and range support
    PLANNING --> DOWNLOADING : chunk plan built, resume state loaded
    DOWNLOADING --> DOWNLOADING : chunk retried after failure
    DOWNLOADING --> VERIFYING : all chunks complete
    VERIFYING --> COMPLETED : whole-file hash matches, or none supplied
    VERIFYING --> FAILED : whole-file hash mismatch
    DOWNLOADING --> FAILED : retries exhausted
    COMPLETED --> [*]
    FAILED --> [*]

    3.2 Chunk State Machine¶

    stateDiagram-v2
    [*] --> PENDING
    PENDING --> DOWNLOADING : worker dispatched
    DOWNLOADING --> VERIFYING : range stream complete
    VERIFYING --> COMPLETED : SHA-256 matches
    VERIFYING --> RETRYING : SHA-256 mismatch, whole chunk discarded
    DOWNLOADING --> RETRYING : transport error or timeout
    RETRYING --> PENDING : backoff with jitter
    RETRYING --> FAILED : max_retries exhausted
    COMPLETED --> [*]
    FAILED --> [*]

    4. Data Path Formulations¶

    4.1 Chunk Download and Hashing¶

    Each worker issues an HTTP range GET and streams the response, computing an incremental SHA-256 over a 64 KB buffer as bytes arrive. Bytes are written at their absolute offset via os.pwrite through SparseFileWriter, so no reassembly pass is needed.

    The chunk size is currently a fixed configuration value. The BL-DCS controller (algorithms/adaptive_chunker.py) computes a size from measured bandwidth, RTT and loss, but is not yet called by the engine — see ALGORITHMS.md.

    4.2 Verification¶

    On arrival, each chunk's digest is compared against the expected value with hmac.compare_digest. A mismatch discards the whole chunk and re-fetches it.

    Whole-file verification, when an expected digest is supplied, re-reads the completed file from disk — an O(N) I/O pass.

    Earlier revisions of this section described a second hash layer (LtHash) giving O(1) whole-file verification by summing chunk hashes, and a Merkle localization path that avoided full chunk re-transmission. Neither is implemented.

    5. Concurrency and Scheduling¶

    Workers are drawn from a bounded pool (max_parallel_workers) and pull pending chunks from shared state; httpx connection limits are set to match the pool size.

    EXP3.S mirror routing (algorithms/mirror_bandit.py) and straggler detection with range bisection (algorithms/work_stealer.py) are implemented and unit-tested but are not yet called by the engine.

    6. Error Recovery¶

    Transient failures are retried with exponential backoff and jitter (download_engine.py:643-652). A chunk that fails verification is discarded and re-fetched in full. Completed chunks are checkpointed to the resume state file, so an interrupted transfer resumes at chunk granularity rather than restarting.

    There is no forward error correction and no sub-chunk corruption localization on the download path.

    7. Direct Sparse Write Data Flow¶

    Download Initialized (--direct-write)
       │
       ▼
[ Pre-allocate target file ] ──▶ posix_fallocate(fd, 0, file_size)
       │
       ▼
[ Launch Worker Coroutines ]
       │
       ├── Worker 0 ──▶ fetch chunk 0 ──▶ verify SHA-256 ──▶ os.pwrite(fd, buf, 0)
       ├── Worker 1 ──▶ fetch chunk 1 ──▶ verify SHA-256 ──▶ os.pwrite(fd, buf, 8388608)
       └── Worker N ──▶ fetch chunk N ──▶ verify SHA-256 ──▶ os.pwrite(fd, buf, offset_N)
       │
       ▼
[ All Chunks Verified & Written ]
       │
       ▼
[ os.fsync(fd) & Whole-File SHA-256 Check ]
       │
       ▼
[ Download Complete — Zero Assembly Delay ]
